## 1. Выполнение технического чеклиста

Работу я выполнял в виртуальной машине Ubuntu 22.04. Bash-скрипт создаёт каталог пользователя. HTTP-сервер в Docker отдаёт созданные файлы через Nginx с TLS. Контейнером управляет systemd. Для работы с хранением данных в проекте есть RAID 1 и LVM.

Блоки "Пример вывода" показывают, как выглядит успешная проверка. Это примеры, а не записи терминала моей виртуальной машины.

### 1.2. Скрипт автоматизации

Скрипт `script.sh` принимает имя пользователя и создаёт каталог `~/sysadmin-users/<имя>`. Внутри он записывает файл `.bashrc` с алиасом `ll`. Сведения о создании каталога попадают в `~/sysadmin-setup.log`.

**Команда:**

```sh
./script.sh alex
```

**Сохранённый вывод из `sample_output.txt`:**

```text
Привет, alex!
Создан каталог: /home/ubuntu/sysadmin-users/alex
Создан файл: /home/ubuntu/sysadmin-users/alex/.bashrc
Запись добавлена в лог: /home/ubuntu/sysadmin-setup.log
```

**Команда проверки созданного файла:**

```sh
cat ~/sysadmin-users/alex/.bashrc
```

**Пример вывода:**

```text
# Bash configuration for alex
alias ll="ls -lah"
```

После запуска остаются каталог пользователя, конфигурация Bash и запись в журнале. Если каталог уже есть, скрипт завершает работу с ошибкой. Это защищает `.bashrc` от перезаписи.

### 1.3. Сборка Docker-образа и запуск контейнера

За основу Dockerfile взят образ `ubuntu:22.04`. При сборке устанавливается Python 3, а скрипт копируется в `/usr/local/bin/script.sh`. Рабочий каталог и значение `HOME` заданы как `/var/www`. HTTP-сервер отдаёт файлы из этого каталога на порту 8080.

**Команда сборки:**

```sh
sudo docker build -t my-script .
```

**Пример вывода, заключительный фрагмент:**

```text
exporting to image
exporting layers done
naming to docker.io/library/my-script done
```

**Команды запуска и проверки:**

```sh
sudo docker run -d -p 127.0.0.1:8080:8080 --name my-app my-script
sudo docker ps --filter name='^/my-app$' \
  --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
```

**Пример вывода `docker ps`:**

```text
NAMES    IMAGE       STATUS         PORTS
my-app   my-script   Up 2 minutes   127.0.0.1:8080->8080/tcp
```

После сборки появляется образ `my-script`. Статус `Up` означает, что контейнер работает. Порт приложения доступен только внутри виртуальной машины. Внешние запросы принимает Nginx.

### 1.4. RAID 1 и LVM

Скрипт `bootstrap.sh` в режиме `base` создаёт RAID 1 и LVM. Для RAID он выделяет два файла по 512 MiB и подключает их через loop-устройства. Из них собирается массив `/dev/md0`. На нём создаётся файловая система ext4 с точкой монтирования `/mnt/raid`.

Для LVM используется третий файл. На нём создаются группа `vg_data` и логический том `lv_logs` объёмом 200 MiB. Том монтируется в `/mnt/logs`.

**Команда создания на чистом стенде:**

```sh
sudo bash bootstrap.sh base
```

**Команды проверки:**

```sh
cat /proc/mdstat
sudo vgs vg_data
sudo lvs -o lv_name,vg_name,lv_size vg_data
df -h /mnt/raid /mnt/logs
```

**Пример вывода `cat /proc/mdstat`, фрагмент:**

```text
Personalities : [raid1]
md0 : active raid1 loop1[1] loop0[0]
      523264 blocks super 1.2 [2/2] [UU]
```

**Пример вывода `vgs` и `lvs`:**

```text
  VG      #PV #LV #SN Attr   VSize   VFree
  vg_data   1   1   0 wz--n- 508.00m 308.00m

  LV      VG      LSize
  lv_logs vg_data 200.00m
```

**Пример вывода `df -h`:**

```text
Filesystem                   Size  Used Avail Use% Mounted on
/dev/md0                     487M   24K  451M   1% /mnt/raid
/dev/mapper/vg_data-lv_logs   189M   24K  175M   1% /mnt/logs
```

Состояние `[UU]` означает, что оба участника RAID доступны. Команды LVM показывают группу и логический том. В выводе `df` видны устройства и точки монтирования. Номера loop-устройств и свободное место могут отличаться на другой ВМ.

### 1.5. Nginx как обратный прокси

В файле `nginx/my-app.conf` настроено перенаправление с HTTP на HTTPS. После обработки TLS Nginx отправляет запрос на `http://127.0.0.1:8080`. Приложение также получает заголовки `Host`, `X-Real-IP`, `X-Forwarded-For` и `X-Forwarded-Proto`.

**Команда:**

```sh
sudo nginx -t
```

**Пример вывода:**

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

Проверка проходит, если в конфигурации нет ошибок и Nginx может прочитать сертификат и ключ. Чтобы проверить передачу запросов приложению, нужен отдельный запрос по HTTPS.

### 1.6. TLS-сертификат и ответ по HTTPS

Для учебного сервиса выбран самоподписанный сертификат OpenSSL. Nginx читает его из `/etc/ssl/certs/my-app.crt`. Закрытый ключ хранится в `/etc/ssl/private/my-app.key`.

**Команда создания сертификата:**

```sh
sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/my-app.key \
  -out /etc/ssl/certs/my-app.crt \
  -subj "/CN=my-app.local"
sudo chmod 600 /etc/ssl/private/my-app.key
```

**Команды проверки:**

```sh
curl -I http://127.0.0.1/
curl -kI https://127.0.0.1/
```

**Пример вывода, основные заголовки:**

```text
HTTP/1.1 301 Moved Permanently
Server: nginx/1.18.0 (Ubuntu)
Location: https://127.0.0.1/

HTTP/1.1 200 OK
Server: nginx/1.18.0 (Ubuntu)
Content-Type: text/html; charset=utf-8
```

Код `301` означает перенаправление на HTTPS. Код `200` означает успешный ответ сервиса через TLS. Для самоподписанного сертификата в команде указан ключ `-k`. Он отключает проверку доверия к сертификату и соответствия имени узла.

### 1.7. Systemd-служба

Служба `my-app` описана в файле `systemd/my-app.service`. Параметры `After=docker.service` и `Requires=docker.service` задают зависимость от Docker и порядок запуска. Команда `docker start -a my-app` запускает готовый контейнер и передаёт его вывод в systemd.

**Команды установки и включения:**

```sh
sudo docker stop my-app
sudo cp systemd/my-app.service /etc/systemd/system/my-app.service
sudo systemctl daemon-reload
sudo systemctl enable --now my-app
```

**Команды проверки:**

```sh
sudo systemctl is-enabled my-app
sudo systemctl status my-app --no-pager -l
```

**Пример вывода, основные строки:**

```text
enabled

* my-app.service - my-app service
     Loaded: loaded (/etc/systemd/system/my-app.service; enabled; vendor preset: enabled)
     Active: active (running)
```

Статус `enabled` означает, что служба включена в автозапуск. Статус `active (running)` означает, что она сейчас работает. При завершении процесса с ошибкой systemd перезапускает его по правилу `Restart=on-failure`.

### 1.8. Журналы приложения и Nginx

Через `docker start -a` сообщения приложения попадают в журнал systemd. Nginx сохраняет запросы в `/var/log/nginx/access.log`. Ошибки записываются в `/var/log/nginx/error.log`.

**Команды проверки сразу после тестового запроса:**

```sh
curl -kI https://127.0.0.1/
sudo journalctl -u my-app --since '2 minutes ago' --no-pager -o cat
sudo tail -n 5 /var/log/nginx/access.log
sudo tail -n 5 /var/log/nginx/error.log
```

**Пример вывода `journalctl`, строка тестового запроса:**

```text
127.0.0.1 - - [26/Oct/2026 09:00:00] "HEAD / HTTP/1.0" 200 -
```

**Пример записи `access.log` для того же запроса:**

```text
127.0.0.1 - - [26/Oct/2026:09:00:00 +0000] "HEAD / HTTP/1.1" 200 0 "-" "curl/7.81.0"
```

Если файл `error.log` пуст, команда `tail` ничего не выводит. Записи Nginx и приложения можно сопоставить по времени и пути запроса. Код `200` в обеих записях показывает успешное прохождение запроса через прокси до приложения.

## 2. Архитектурные решения

### 2.1. Почему я выбрал вариант В: setup-скрипт

Ещё в детстве я разворачивал серверы Minecraft и делал их резервные копии. Приходилось раскладывать файлы по каталогам, а потом собирать их для бэкапа. Мне хотелось автоматизировать эту рутину.

Поэтому в ДЗ1 я выбрал вариант В: setup-скрипт для подготовки каталога пользователя и настройки Bash. Он принимает имя пользователя и выполняет несколько действий одной командой. Результат легко проверить: появляются каталог, `.bashrc` и запись в журнале.

Скрипт работает внутри `$HOME`, поэтому права администратора ему не нужны. Без аргумента он выдаёт ошибку. Если каталог уже существует, скрипт останавливается и не меняет старую конфигурацию. Учётную запись Linux через `useradd` он не создаёт.

### 2.2. Задачи RAID 1 и LVM

RAID 1 хранит копию данных на каждом из двух участников массива. Поэтому полезная ёмкость двух одинаковых дисков примерно равна ёмкости одного. Если диски физически независимы, массив может продолжать работу после отказа одного из них. Резервные копии всё равно нужны.

В моей лабораторной роль дисков выполняют файлы, подключённые через loop-устройства. Так можно изучить RAID внутри ВМ без отдельных физических дисков. Оба файла лежат на одном носителе, поэтому от его отказа такой массив не защитит.

LVM позволяет распределять доступное место между логическими томами. В проекте физический том входит в группу `vg_data`. Из неё выделен том `lv_logs`. Оставшееся место можно использовать для его расширения или создания новых томов. Сам по себе обычный линейный том LVM не дублирует данные.

Для RAID используются первые два образа дисков. LVM работает на третьем. Поэтому зеркало `/dev/md0` не защищает том `lv_logs`. Можно собрать LVM поверх RAID по схеме RAID -> PV -> VG -> LV. В этой работе они настроены отдельно. Каталог `/mnt/logs` служит точкой монтирования LVM-тома. Журналы сервисов на него не перенесены.

### 2.3. Почему выбран самоподписанный сертификат

Для учебной ВМ я выбрал самоподписанный сертификат. Для него не нужен публичный домен и подтверждение прав на него. OpenSSL создаёт сертификат и ключ на самой машине. Nginx использует их для HTTPS.

Браузер и curl по умолчанию не доверяют такому сертификату. Поэтому в проверочной команде есть `-k`. Чтобы обойтись без него, нужна доверенная цепочка сертификатов. Имя или IP сервиса также должны быть указаны в поле SAN. Сертификат выдан на 365 дней. Права `600` ограничивают доступ к закрытому ключу.

### 2.4. Сравнение с альтернативами

| Решение                    | Альтернатива                                          | Причина выбора                                                           |
| -------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------ |
| Bash setup-скрипт          | Создание файлов вручную                               | Одна команда готовит каталог и записывает результат в журнал             |
| Docker                     | Установка приложения прямо в Ubuntu                   | Среда и команда запуска описаны в Dockerfile                             |
| Nginx перед приложением    | Прямой доступ к Python HTTP-серверу                   | Nginx обрабатывает TLS и перенаправляет HTTP на HTTPS                    |
| Самоподписанный сертификат | Let's Encrypt или другой публичный центр сертификации | Можно настроить TLS без публичного домена                                |
| Systemd                    | Ручной запуск контейнера                              | Служба задаёт зависимости, автозапуск, остановку и перезапуск при ошибке |
| Loop-устройства            | Отдельные физические диски                            | Вся лабораторная помещается в одной ВМ                                   |

### 2.5. Взаимодействие компонентов

Клиент обращается к Nginx по HTTPS. Nginx обрабатывает TLS и передаёт HTTP-запрос на `127.0.0.1:8080`. Docker направляет его в контейнер `my-app`. Python-сервер отдаёт файлы из `/var/www`. В этом каталоге находятся результаты работы скрипта и его журнал.

Systemd запускает готовый контейнер и собирает его вывод. Образ нужно собрать, а контейнер создать до включения службы. Скрипт `bootstrap.sh` отвечает за RAID и LVM. Docker, Nginx, TLS и systemd настраиваются отдельными командами.

Данные хранятся в записываемом слое контейнера. Остановка и повторный запуск их не удаляют. Чтобы сохранить файлы после удаления и пересоздания контейнера, нужен volume или bind mount. В Dockerfile скрипт запускается в фоне. Поэтому одной проверки HTTP недостаточно: нужно также проверить созданные файлы.
